# ddd-docmap 요구사항

문서 기준: 2026-10-27. 문서 기반 개발(Doc-Driven Development)을 사용하는
프로젝트를 위한 독립 CLI 도구다. DDD는 이 문서에서 이 의미로 사용한다.

[설계](./DESIGN.md) · [구현 계획](./IMPLEMENT.md) · [수동 검증](./MANUAL_TEST_CHECKLIST.md)

## 목적과 사용 맥락

개발자가 프로젝트 곳곳에 쌓인 문서를 찾고, 기능의 상하위 구조와 관련 문서를
한눈에 파악하도록 돕는다. 개발 중 CLI 명령을 실행해 로컬 브라우저에서 사용한다.

특정 저장소에 포함된 기능이 아니라 여러 프로젝트에 설치하는 별도 패키지다.
문서를 업무 진행률로 해석하는 기능보다 문서 탐색과 읽기에 우선순위를 둔다.

## 문서 위치와 구현 범위

이 프로젝트의 기준 문서는 docs/의 이 4종이다. 계획을 별도 파일에 복제하지 않는다.

| 위치 | 책임 | 현재 상태 |
| --- | --- | --- |
| ../bin/ddd-docmap.js | CLI 실행 진입점 | 서버 실행·루트 옵션·종료 동작 |
| ../src/cli.js | 인자·브라우저 열기·포그라운드 수명주기 | Phase 2 구현 |
| ../src/collector/ | 문서 수집·계층·설정·검색 인덱스 | Phase 4 구현 |
| ../src/server/ | loopback·서식/참조·검색·SSE·감지기 | Phase 4 구현 |
| ../src/web/ | 지도·읽기·검색·실시간 갱신·탐색 상태 | Phase 4 구현 |
| ../test/ | 수집·설정·메타데이터 테스트와 가상 예제 생성기 | 작성 |

설치되는 프로젝트는 입력 데이터의 소유자다. 도구의 설치 위치와 문서를 읽을
프로젝트 위치를 구분한다.

## 요구사항의 상태

- **확인됨**: 사용자가 직접 요청했거나 선택한 내용.
- **설계 제안**: 기본 동작을 구체화한 초안. 사용자 확인 사항과 혼동하지 않는다.
- **구현됨**: 실제 코드와 검증 근거가 있는 상태. 요구사항 확인과 별개다.
- 세부 결정은 설계의 DC/IC 체크리스트에서 관리한다. TBD를 임의로 확정된 것으로 표시하지 않는다.

## 첫 사용 가능 단계와 확장

1. 문서 수집과 기능 계층을 만든다.
2. CLI로 서버·브라우저를 열고 카드와 문서 선택을 연결한다.
3. Markdown 읽기와 기본 링크를 완성한다. 이 지점이 첫 사용 가능 단계다.
4. 검색·자동 갱신·이동 문서 연결을 추가한다.
5. Test Hardening과 Integration Test를 거쳐 배포를 준비한다.

부분 문서 묶음의 탐색은 수집 단계부터 다룬다. 실제 프로젝트를 사용할 때
문서 4종을 모두 새로 만들거나 기존 파일을 옮기는 작업을 전제로 하지 않는다.

## 설치·실행 제약

- 저장소 이름은 ddd-docmap이다. 명령 이름은 ddd-docmap을 사용한다.
- 현재 manifest의 이름은 @superlucky84/ddd-docmap이다. npm 등록 가능 여부는 미확인이다.
- 현재 패키지는 private이며 라이선스는 미선정이다. 공개 GitHub와 npm 배포를 구분한다.
- CLI 뼈대의 최소 Node.js는 22다. 검증된 실행 환경은 현재 macOS / Node.js 24.21.0이다.
- 최종 지원 OS와 최소 버전 검증은 배포 전 결정한다.
- 대상 프로젝트의 소스 빌드나 설정 파일 실행 없이 Markdown을 읽는다.
- 웹 화면은 배포 패키지에 미리 빌드해 포함하는 방식을 제안한다.
- 본문과 인덱스는 로컬에서 처리하며 기능 사용에 외부 계정 로그인을 요구하지 않는다.

## 데이터와 기존 문서

- 원본 Markdown과 문서 간 링크가 기준이다. 도구가 원본을 편집하거나 이동하지 않는다.
- 설정은 선택 사항이며 기존 문서에 별도의 메타데이터 작성을 요구하지 않는다.
- 기본 발견 범위 밖의 문서는 설정으로 추가할 수 있게 한다.
- 인덱스는 재생성 가능한 파생 데이터다. 장기 보관할 별도 문서 데이터베이스를 요구하지 않는다.
- 설정 형식을 변경할 때 버전을 구분하고, 읽을 수 없는 버전은 명확히 안내한다.

## 오류와 규모

문서 0개, 읽기 실패, 잘못된 설정, 존재하지 않는 링크를 서로 다른 상태로 안내한다.
문서 하나의 읽기 실패가 다른 정상 문서의 탐색까지 막지 않도록 제안한다.

대표 성능 예제는 가상 Markdown 300개로 시작한다. 이 숫자는 지원 상한이 아니다.
수집·검색·갱신 시간을 측정하고 환경과 결과를 기록한 뒤 허용 시간을 정한다.
측정하지 않은 속도나 지원 문서 수를 성능 보장으로 표시하지 않는다.
Phase 5에서는 재현 가능한 F-08 생성기와 측정 명령을 남기며 유휴 polling의 CPU와 메모리도 기록한다.

## 범위 밖

첫 제품 범위에서 문서 편집, 업무 진행률 자동 판정, 조직 통합 대시보드,
중앙 호스팅, 원격 저장소 동기화, AI 요약, Markdown 플러그인 생태계는 다루지 않는다.
